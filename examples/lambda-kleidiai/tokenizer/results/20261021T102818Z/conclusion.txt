T0 characterises; it does not optimise. Tokenisation is negligible end to end. The claim that the tokenizer is implemented in Python is false. The deployed tokenizer is Hugging Face tokenizers 0.23.2, a Rust core behind a PyO3 binding: tokenizers.abi3.so is an aarch64 ELF built by rustc 1.98.0 and statically links the onig, regex and rayon crates. Python makes only the from_file, encode and encode_batch calls.

LAMBDA. All Lambda numbers are reused from P3 run 20261020T231634Z (P1's deployed zip 26eb2651, us-east-2). T0 made no new AWS spend. cProfile figures are upper bounds; P3 measured cProfile at +113 ms Init.
- Warm (n=500: 481 on CPU part 0xd40, 19 on 0xd0c). Tokenisation (HiddenStateEngine.fit) has p50 0.83 ms, p99 2.4 ms. That is 0.12% of handler time by mean. lkaisamp CPU samples put tokenizers.so at 0.06% of warm CPU.
- Cold first request (n=50: 36 on 0xd40, 7 on 0xd0c, 7 on 0xd4f). fit p50 is 0.53 ms, 0.2% of the request. Tokenizer init (Tokenizer.from_file) has p50 0.83 s. It runs in PR #77's background load thread after Init returns, so its share of REPORT Init Duration is 0%. On the cold first request (P1 p50 36.0 s) it is at most 2.3%. lkaisamp puts tokenizers.so at 2.1% of init CPU.
- SnapStart. Tokenizer init runs at import, before the snapshot (snapshot-init from_file p50 0.98 s), and is not re-run on restore.
- Restored first request (n=50: 48 on 0xd40, 2 on 0xd0c). fit p50 is 1.7 ms, but p90 is 32 ms and max is 138 ms. That is 1.3% of handler time by mean. The tail is almost all inside encode_batch. lkaisamp CPU sees only 0.49% in tokenizers.so, so the tail is mostly waiting, not tokenizer compute. Restored-page faults are a likely cause but are untested.

FIXED HOST. Graviton3 DevSpace (CPU part 0xd40), P1's pinned Lambda python3.12 image, the deployed bytes, pinned to 4 free CPUs. These numbers are not Lambda latency.
- Init: from_file p50 0.61 s, single-threaded (CPU time equals wall time). Its RSS is 161 MB.
- Steady state: fit on P1's five requests takes 0.14–1.14 ms, at 0.52–0.82 M tokens/s. A full 4096-token window takes 12 ms. An over-window state, which is trimmed to the window, takes 20 ms. Python GC never collected in these cases, and tracemalloc peaks at 4–22 kB per P1 request.
- Repeatability: runs r2 and r3 were 22 minutes apart. Single-threaded cases agree within 1.2–4.7% (p50). Multi-question cases use rayon encode_batch and moved up to +32%, because another job shared r3's CPUs. All but one case (handler-warmup, +1.9%) have overlapping per-round p50 ranges. Run r1 shared its CPUs with other jobs and is published only as a contended control.

PROFILE (perf record, 999 Hz, dwarf; fixed host).
- Steady-state self time: 45% glibc malloc/free, 43% Rust tokenizer code, 2.2% libpython.
- Inclusive: rayon 55%, onig pre-tokenizer regex 21%, ByteLevel 18%, byte-to-char offsets 13%, BPE cache 10%.
- Init: serde_json parsing of the 20 MB tokenizer.json is 83% inclusive, plus HashMap builds.
- Classification. Steady state is compute plus allocation (allocator self time, not Python GC). Init is compute-bound.
- Nothing is classified as memory-bandwidth-bound. This VM's PMU exposes only cycles; instructions and cache events are "not supported".
- Profiler overhead against an unprofiled soak: perf stat +1.3%, perf record +35%. No profiled timing is reported as latency.

T1–T3. These follow from the measured headroom, not from targets set in advance.
- T1 (optimise Python): no headroom. Python is about 2% of tokenizer samples, and tokenisation is under 0.2% of a warm request.
- T2 (compiled hot paths): already compiled. The one material cost is from_file at 0.6–0.8 s on the on-demand cold path, at most 2.3% of a 36 s cold request. SnapStart already removes it from restores.
- T3 (an off-the-shelf tokenizer): no warm-latency case. At most about 0.8 s of cold init is reachable. Any replacement must pass the parity suite.
Recommendation: cancel T1–T3, or narrow one to "cold-path tokenizer.json load" plus a restore-tail check.

CORRECTNESS. The parity suite has 217 cases and 61,409 token ids, matched at 100% on aarch64 with 0.23.2 and on x86_64 with 0.23.3. A single changed id fails it.

LIMITATIONS.
- No new Lambda run. The Lambda shares come from P3's cProfile and lkaisamp arms, which ran on the P1 zip under a profiler. They are upper bounds, with n=50 per start class and 500 warm. The REPORT-only arm has no tokenizer split.
- The fixed host is one Graviton3 DevSpace (0xd40) shared with other cards' jobs. It ran on 4 free CPUs, not Lambda's 6. Each run's host-*.txt lists the load average and the other jobs' CPU affinity.
- The repeat runs were on the same host on the same day. No second host of the same part was available.
- Multi-question (rayon) cases are sensitive to co-tenancy, so their r2/r3 deltas reflect the host, not the code.
- The PMU on this VM exposes only cycles. Instruction, cache and stall counters are not supported, so no bandwidth or IPC claim is made.
- Graviton2 (0xd0c) and Graviton4 (0xd4f) appear only in the small Lambda samples (n=7 cold, 19 warm and 2 restore on 0xd0c; n=7 cold on 0xd4f). They show the same ordering.
- The fixed-host scripts that ran differ from commit 43d9a0f only in formatting and a helper rename (PROVENANCE.txt).
